# HW3: Семантический анализатор языка Funny
Реализация семантического анализа и типизации абстрактного синтаксического дерева (AST) для языка Funny.

## Возможности

- **Таблицы символов:** поддержка глобальной и локальных областей видимости, проверка повторных объявлений и использования необъявленных имен.
- **Проверка типов:** строгая типизация для арифметики, логики, сравнений, индексации массивов и вызовов функций.
- **Аннотированный AST:** каждый узел выражения получает поле `type` после успешного анализа.
- **Режим паники:** анализатор не падает при первой ошибке, а продолжает обход AST, собирая все семантические ошибки за один проход.

## Поддерживаемые типы и правила

| Конструкция | Правило типизации |
|---|---|
| Литералы | `число` → `int`, `true`/`false` → `bool` |
| Арифметика (`+`, `-`, `*`, `/`) | Требует `int` и `int`, возвращает `int` |
| Логика (`and`, `or`, `not`, `->`) | Требует `bool`, возвращает `bool` |
| Сравнения (`==`, `<`, `>` и др.) | Требует `int` и `int`, возвращает `bool` |
| Массивы (`arr[i]`) | `arr` должен быть `int[]`, `i` должен быть `int`. Результат: `int` |
| Присваивание (`x = expr`) | Тип цели должен строго совпадать с типом выражения |
| Вызов функции | Строгая проверка имени, количества и типов аргументов |

*Примечание: Неявные преобразования типов и перегрузка функций не поддерживаются.*

## Как работает анализатор

Анализ выполняется в два прохода:

1. **Регистрация:** все функции и формулы добавляются в глобальную таблицу символов. Это позволяет вызывать функции, объявленные ниже по тексту.
2. **Проверка:** для каждой функции создается локальная область видимости, куда добавляются параметры, возвращаемые значения и локальные переменные (`uses`). Затем AST обходится снизу вверх, типы вычисляются и записываются в поле `type` каждого узла.

### Пример аннотированного AST

Для кода `result = a + b;` узел бинарной операции будет выглядеть так:

```json
{
  "type": "BinaryOp",
  "op": "+",
  "left": { "type": "Name", "name": "a", "type_annotation": "int" },
  "right": { "type": "Name", "name": "b", "type_annotation": "int" },
  "type_annotation": "int"
}
```

*(Поле `type` указывает на класс узла, а `type_annotation` (или `type` внутри узла) хранит выведенный тип данных).*

## Установка и запуск

Проект использует только стандартную библиотеку Python.

### 1. Подготовка окружения

```powershell
cd C:\Users\User\Desktop\GitHub\HW03_types

# Создание и активация виртуального окружения (через uv или стандартно)
uv venv
.\.venv\Scripts\Activate
```

### 2. Запуск анализатора

```powershell
# Анализ файла с выводом JSON или ошибок
python main.py example.funny

# Только парсинг (без семантических проверок)
python main.py --no-semantic example.funny
```

*При наличии ошибок они выводятся в `stderr`, а код возврата равен `1`.*

### 3. Запуск тестов

```powershell
python -m unittest test_semantic.py -v
```

*Ожидаемый результат: `18 passed`.*

## Ограничения текущей реализации

1. Узлы AST пока не хранят точные позиции (`line`, `column`) из токенов, поэтому семантические ошибки выводятся без указания строки (это можно легко добавить, расширив базовый класс `Node`).
2. Вывод типов для локальных переменных без явной аннотации реализован в базовом виде: тип переменной `uses` выводится по первому корректному присваиванию. Если первое присваивание содержит ошибочное выражение, тип не выводится.
3. Проверка предусловий (`requires`) и постусловий (`ensures`) ограничена их сохранением в AST; глубокая семантическая валидация предикатов вынесена за рамки базового требования.
